01

卡壳的机制解释：不是能力问题，是表示问题

先定位断点，再谈改进。五条机制，按依赖顺序排列——第 1 条解释了后面四条。

1.1你持有的是「结果态图像」，代码需要的是「过程态序列」

206 你脑中是 1←2←3←4←5；203 你脑中是 1→2→␣→3→4→5。两者都是终点。而代码要的是：读下一帧 → 写指针 → 移动游标 组成的轨迹。

从终点直接跳到代码，等于要求 f(结果) → 源码 一步完成。正确链路是两步：

结果态图⟶ 原子序列（缺失）⟶ 源码 ← 你每次都在这一步之外求解，所以必卡
不要把「图更清楚」当作解法。缺的不是清晰度，是分辨率层级：图是整张，代码是单帧。这是卡壳的唯一数学原因，与天赋、经验、语言熟练度无关。

1.2粒度失配：概念操作 vs 原子操作

你脑内的最小单位是「概念」——「删掉 6」是一个动作。代码的最小单位是「单次赋值」。中间差了一次展开：

你脑内的单位代码里必须展开成展开倍率
「删掉 6」读 cur.next.val → 命中则 cur.next = cur.next.next1 → 2 原子 + 1 决策
「反转一根箭头」nxt = cur.next → cur.next = pre → 两个游标前移1 → 4 原子
「往前找」while cur.next is not None: …1 → 1 循环头 + n 轮

你的思维以概念为单位（高效、抽象、可上卷），代码以赋值为单位（低效、序列化、不可压缩）。中间没有「概念 → 原子」展开器，写第一行时脑内就没有「下一个原子」。这就是「心中有图，手上懵」的语义学定义：你存的是名字，代码要的是动作。

1.3注意力架构：编码时你在做全局推演

链表错误只有三种：断链（丢后继）、丢前驱（删不掉/回不去）、死循环（指针打转）。三者同一个根因：你在写第 3 行时已经开始推演第 9 行，第 3 行的局部状态被挤出。

链表题的正确性只依赖当前局部不变量，完全不依赖全局图。你在编码时加载整张图 → 认知负荷超载 → 局部状态溢出。这是可修的结构问题：编码期只允许持有 3 个变量的状态。

1.4三类记忆被混为一谈（效率低的根因）

层定义你的现状
L1 陈述性看懂、能讲、有图已具备（206/203 你都懂了）
L2 程序性手能自动写出，不需要回忆缺失 —— 所以一写就卡
L3 判据性换皮题能识别出同一模型缺失 —— 206 的坑 203 又踩一遍
INTJ 的吸收瓶颈 90% 发生在 L2 / L3，而他们往往把 L1 的完成误判为任务结束。你不是学得慢，是学得快、停得早：L1 十分钟就通了，然后进入下一题的新鲜感，L2/L3 永远是 0。

2.2你手上只有三层，没有第四层

返回层return 的那个节点return dummy.next—唯一入口

没有第四层。你不能「操作整条链表」——链表不是对象，它是一个从某个盒子出发的可达集合。这句话解释了两件事：为什么「丢失的引用找不回」（没有反向可达），以及为什么「删头必须换返回值或加哨兵」（头的可达集合变了，但你没别的通道通知判题机）。

2.5口诀与骨架：把身份层接回 A1–A6

进门只拿一张贴纸（head）→ 顺 .next 摸盒子 → 只能改盒子的 .next → 出门只交一张贴纸（return）。 七个动作、六个原子、三层身份，一一对应。背口诀，不背题。
动作属于哪层 / 哪个原子为什么
挪贴纸 cur = cur.next变量层 · A5只换视角，结构不动；所以它永远安全，也永远单独不产生效果
改盒子 cur.next = x对象层 · A4唯一能改图的动作；也是唯一会销毁旧信息的动作（顺序公理来源）
造盒子 ListNode(0)对象层 · A6唯一能凭空产生节点的动作；dummy 就是靠它存在
交贴纸 return ...返回层判题机唯一入口；交谁，决定它看见哪条链
七行骨架：每一行都标注「贴纸 / 盒子」建议手抄三遍
1dummy = ListNode(0) # 造盒子（A6）
2dummy.next = head # 改盒子（A4）
3pre = dummy # 贴纸（A5）
4while pre.next: # 读盒子
5 if pre.next.val == val:
6 pre.next = pre.next.next # 改盒子（A4，贴纸不动）
7 else: pre = pre.next # 贴纸（A5）
8return dummy.next # 交贴纸

为什么 INTJ 特别容易卡在这一层：你的建模单位是「关系」，但这里有两套关系叠在一起——名字→对象的绑定关系（可以随便改，无副作用）和对象→对象的边关系（改了就是改图）。混层的瞬间，你的模型会同时出现两个"当前节点"，于是必然卡壳。分开它们，卡壳消失。

03

区间模型：所有指针题共享的那根轴

这一节是通用模块，不只服务链表。它把「双指针 / 滑动窗口 / 链表游标」统一成同一句话：指针题的实质是维护两个区间的边界。

任何指针类题目，在任意一帧都只有三个对象：已处理区间、未处理区间、以及边界游标。正确性不来自你能否想象全图，而来自「已处理区间的不变量」始终成立。

已验证区（不变量在此成立）
未验证区（尚未触碰）
↑ 游标 = 唯一边界
操作只有两种：扩张（把下一个元素纳入已验证区）／ 收缩（把元素踢出窗口）。
编码只有一句判据：每次移动游标之前，确认「已验证区的不变量仍成立」。

3.1同一根轴在三类题上的实例

题族已验证区边界游标不变量
206 反转已反转段（箭头向左）curpre = 已反转段的头
203 删除已确认保留段（无 val）cur（其 next 待校验）cur 指向已确认保留的最后一个节点
滑动窗口窗口内元素（满足约束）[l, r) 半开区间r 之前的全部处理完；窗口内恒满足条件
快慢指针慢指针之前（已确认无环区）slow / fastfast - slow 恒为 k
区间模型是你已有的资产，但要升级一个用法：把「画图」换成「写不变量」。图只能表达一个状态；不变量能表达一整族状态。INTJ 擅长不变量，不擅长逐帧记忆 —— 这正好是你的优势区，别浪费在画图上。

顺带一条工程习惯：区间一律用半开 [l, r)，长度 = r - l，空区间 = l == r，无需 ±1 修正。链表里的对应表达是「cur 指向已确认段的最后一个」，等价于 [dummy.next, cur] 闭区间。

04

原子操作 DSL：链表只有 6 个动作，且写操作只有 1 个

这是本手册的核心资产。掌握它，链表模块从「无数道题」坍缩为「一个操作符的排列组合」。

云主机实测确认：ListNode 实例的读写面只有 val 与 next 两个字段。由此可推出链表领域的最小完备操作集。

编号原子操作代码形态性质
A1读值x.val读，无副作用
A2读后继x.next读，无副作用
A3判空x is None读，无副作用
A4改后继x.next = y唯一的结构写操作 · 破坏性
A5移动游标p = x绑定，不改图
A6新建节点ListNode(v)构造，分配新内存
反转、删除、插入、合并、拆分、环检测修复 —— 全部只是 A4 的时序编排 + A5 的游标管理。你要背的不是题型，是一个操作符的排列组合规则。

4.1顺序公理（唯一必须背死的一条）

A4 是破坏性写：一旦执行，旧的 x.next 永久丢失。因此任何 A4 之前，必须完成所有「需要旧 next 信息」的读取。

✓ 先读后写（正确）
1→2→3 输出 3←2←1

nxt = cur.next  →  cur.next = pre

旧 next 先进 nxt 安全区，A4 执行后仍能找到下一个节点。

✗ 先写后读（实测崩）
1→NULL 23 实测输出 [1]

cur.next = pre  →  nxt = cur.next

写完再读，「下一个」已经是 None，链表在第一个节点处断掉，节点 2、3 成为孤儿。

这不是理论推演。云主机脚本里 wrong_order() 函数对 [1,2,3,4,5] 的实测输出就是 [1]，预期 [5,4,3,2,1]。一条公理覆盖了你 90% 的断链 / 丢后继 / 死循环。

4.2编译规则表：脑内意图 → 原子序列

脑内意图（概念）编译出的原子序列原子编号

4.3命名合法性（206 报错的直接修补）

把 206 的坑固化为一条前置检查，而不是记住那道题：类型名 / 类名 / 导入名，一律禁止作为可写变量。

命名合法性 · 反例与正例Python 3.12
1ListNode = ListNode.next # ✗ 遮蔽类名 → UnboundLocalError
2cur = head # ✓ 游标用独立命名

原因：函数体内任何对 ListNode 的赋值，会让 Python 把它判定为局部变量；此时再写 ListNode(...) 就是在赋值前访问未绑定名。这不是「不熟悉语法」，是命名空间被覆盖。

206. 反转链表 —— 逐帧推演

样例 1 → 2 → 3 → 4 → 5。每一帧只允许做一个原子动作。用「下一步」走完，你会看到「图」与「代码行」在同一帧里对齐。

第 0 轮 / 初始 初始 1 / 22

初始：cur 指向原表头，pre 悬空（新的表尾）。

不变量：pre 指向已反转段的头节点（初始为 None）

5.1三种写法（全部保留，实跑通过）

解法 A｜栈重建法 —— 你的原始思路：线性序列化 → 逆序弹出 → 重建链表。空间 O(n)，逻辑最直观。

A｜栈重建 · O(n) 空间2 次遍历
1class Solution:
2 def reverseList(self, head: ListNode | None) -> ListNode | None:
3 if head is None: # 空链表直接返回
4 return None
5 tmp, cur = [], head
6 while cur: # 阶段1 遍历入栈
7 tmp.append(cur.val)
8 cur = cur.next
9 newHead = ListNode(tmp.pop()) # 阶段2 弹出栈顶作新头
10 t = newHead
11 while tmp: # 阶段3 串成新链表
12 t.next = ListNode(tmp.pop())
13 t = t.next
14 return newHead

这里的 if head is None 不是为了图解——是因为 tmp.pop() 对空数组会抛 IndexError。属于「算法之外的结构性边界」，必须单独记住。

解法 B｜原地双指针 —— 最优范式，空间 O(1)，面试首选。

B｜双指针原地 · O(1) 空间1 次遍历 · 3 个变量
1class Solution:
2 def reverseList(self, head: ListNode | None) -> ListNode | None:
3 pre = None
4 cur = head
5 while cur:
6 nxt = cur.next # A2｜顺序公理：必须在写之前
7 cur.next = pre # A4｜唯一写操作，破坏性
8 pre = cur # A5｜cur 划入已反转段
9 cur = nxt # A5｜进入下一个待反转节点
10 return pre

解法 C｜递归 —— 拓展范式，栈深 = 链表长度，适合理解分治结构。

C｜递归 · O(n) 调用栈慎用于长链
1class Solution:
2 def reverseList(self, head: ListNode | None) -> ListNode | None:
3 if head is None or head.next is None: # 递归基
4 return head
5 newHead = self.reverseList(head.next) # 子问题：反转后半段
6 head.next.next = head # A4｜后驱指回自己
7 head.next = None # A4｜断开旧指向
8 return newHead

203. 移除链表元素 —— 逐帧推演

样例 1 → 2 → 6 → 3 → 4 → 5 → 6，val = 6。重点看两处：命中后 cur 为什么不动；dummy 如何把「head 是否被删」这张额外分支图归并掉。

第 0 步 / 建哨兵 A6 1 / 16

建哨兵 dummy 并绑定 head：从此 head 是否被删都不改变代码路径。

不变量：cur 指向「已确认保留」的最后一个节点（初始为 dummy）

6.1三种写法（全部保留，实跑通过）

解法 A｜哨兵 dummy —— 面试标准。核心价值不是「省事」，而是把两张图归并成一张。

A｜dummy 哨兵 · O(1) 空间统一路径，无头特判
1class Solution:
2 def removeElements(self, head: ListNode | None, val: int) -> ListNode | None:
3 dummy = ListNode(0) # A6
4 dummy.next = head # A4
5 cur = dummy # A5｜cur 站前驱位
6 while cur.next is not None: # 看后继，不看自己
7 if cur.next.val == val:
8 cur.next = cur.next.next # A4｜命中：跨越，cur 不动
9 else:
10 cur = cur.next # A5｜保留：才前移
11 return dummy.next # 不是 cur，也不是 head

解法 B｜无哨兵（你的原始思路） —— 必须单独一段循环处理头部，代码被切成两段。

B｜无 dummy头部必须特判
1class Solution:
2 def removeElements(self, head: ListNode | None, val: int) -> ListNode | None:
3 while head and head.val == val: # 独立处理：头部连续命中
4 head = head.next
5 cur = head
6 while cur and cur.next:
7 if cur.next.val == val:
8 cur.next = cur.next.next
9 else:
10 cur = cur.next
11 return head # 注意：head 可能已被改

解法 C｜递归 —— 先修好子链，再决定当前节点去留。

C｜递归O(n) 栈
1class Solution:
2 def removeElements(self, head: ListNode | None, val: int) -> ListNode | None:
3 if head is None:
4 return None
5 head.next = self.removeElements(head.next, val) # 先修好后继
6 return head.next if head.val == val else head

6.3避坑清单（与 206 同源）

  • 01游标直接站到待删节点（cur = head）→ 删掉后找不到前驱。删除必须站前驱。
  • 02删除后又写 cur = cur.next → 连续命中漏删（[7,7,7,7] 必错）。命中时 cur 必须原地不动。
  • 03循环条件写 while cur is not None → 会去读越界位置的 cur.next.val。必须是 while cur.next。
  • 04返回 cur / 返回 head → 必须 return dummy.next。cur 循环结束时站在尾节点。
  • 05类名当循环变量（206 原坑 ListNode = ListNode.next）→ UnboundLocalError。

判据库 R1–R5：把题解上卷成规则

你之前的复盘存的是「203 的正确代码」——它挂在知识树的叶子上，遇到 19 / 82 时调不出来。改成 if-then 判据后，会自动上卷成一个「链表删除范式」节点。

R1

THEN 先建 dummy，结尾 return dummy.next
依据：把「head 存活 / head 被删」两张图归并成一张
R2
IF 需要修改 next 指向
THEN 先确认旧 next 是否还被需要；需要就先读进临时变量
依据：顺序公理 · A4 是破坏性写
R3
IF 删除完成后，新的 next 可能同样命中
THEN 游标不前移，原地再判一次
依据：不变量 · cur = 已确认保留的最后一个节点
R4
IF 循环内需要访问 cur.next.val
THEN 条件写成 while cur.next is not None
依据：读后继即要求后继存在
R5
IF 函数需要返回链表
THEN return dummy.next 或 return pre，永不 return cur
依据：cur 在循环终止时必为 None 或尾节点
判据与题解的区别只有一个：判据能被别的题调用，题解只能被这道题调用。这五条写进笔记后，19（删倒数第 N 个）、82（删排序链表重复元素 II）、83（删重复元素）都能直接命中。
